DeadLock & The Gentlemen: Two Case Studies in Real Ransomware Encryption

Two real, unrelated families — grounded in Microsoft Threat Intelligence's 2026 technical breakdowns.

One case study risks looking like a quirky one-off. Two, from unrelated operations, start to show what actually generalizes. DeadLock and The Gentlemen were built independently, in different languages, by different groups — and they land on the same core encryption primitives while differing almost everywhere else. That's the pattern worth taking away: not these two specific families, but the shape underneath them, which is exactly what Module 3's checklist and decision tree are built to catch.

CASE STUDY A

DeadLock: A Rust Encryptor With No Fixed Address

First seen

Jul 2025

Language

Rust

Extension

.dlock

Claimed victims

80+ / 4 continents

Execution & privilege escalation

DeadLock accepts an optional target-path argument. Given one, it skips straight to encrypting that path — no teardown, no evasion, just the payload. Run with no argument on a non-elevated host, it goes for admin rights instead: it drops a randomly-named eight-character .cmd file and launches it through ShellExecuteW with the RunAs verb, surfacing a standard UAC prompt. Deny it and the malware simply asks again — up to ten times — before giving up. Once elevated, it enables SeDebugPrivilege, SeBackupPrivilege, SeRestorePrivilege, and SeTakeOwnershipPrivilege — together enough to interact with protected processes, bypass file ACLs outright, and seize ownership of anything it needs.

Pre-encryption teardown T1489 T1068

Before a single byte gets encrypted, DeadLock walks the running Win32 service list against a built-in stop-list and disables and kills every match — Windows Defender, the Volume Shadow Copy service, Windows Backup, Hyper-V components, and Active Directory services all appear on it. A parallel process kill-list targets specific software by name: security tools (MsMpEng, SecurityHealthService, Windows SmartScreen), cloud-sync clients (OneDrive, Dropbox, Google Drive — removing cloud-based recovery options specifically, not just local ones), remote-access tools, and even Windows Explorer and PowerShell themselves. It empties the Recycle Bin on every drive, closing off the easiest manual recovery path a user might reach for.

Some observed intrusions layered a BYOVD loader on top of this: Cisco Talos documented a DeadLock campaign exploiting CVE-2024-51324, a flaw in a legitimately signed Baidu Antivirus driver, to reach kernel-level (Ring 0) access and kill EDR processes that would otherwise survive even an elevated account.

Encryption: Curve25519 + XChaCha20, throttled and tiered

DeadLock's cryptographic design is the exact hybrid pattern from Module 1, with a specific, verified pair of algorithms: for each file, it generates a fresh 32-byte XChaCha20 key and encrypts the contents with it, then generates a per-file ephemeral Curve25519 keypair and runs an elliptic-curve Diffie–Hellman exchange against the operators' embedded public key. The resulting shared secret wraps the XChaCha20 key using the NaCl crypto_box construction — XSalsa20 plus Poly1305 for authenticated encryption — before it's appended to the encrypted file. Every file gets its own keypair and its own shared secret, which is precisely the "unique key per run" property Module 1 described, applied per file rather than per victim.

On top of that, DeadLock encrypts in 512-byte blocks at regular intervals rather than reading a file straight through — the intermittent-encryption pattern from Module 3, concretely. The engine runs behind the resource-aware gatekeeper covered there too: new files stop being dispatched once memory or CPU load runs high, while anything already mid-file is left to finish, so the process never visibly stalls partway through a write.

Registry & icon branding T1112

Encrypted files get rebranded, not just renamed. DeadLock drops a custom .ico file to C:\ProgramData\<UID>.ico and points HKLM\SOFTWARE\Classes\.dlock\DefaultIcon at it, so every locked file shows the group's icon in Explorer the moment encryption finishes — a small, deliberate signal that something's wrong before the victim even opens a note.

Anti-forensics & geofencing T1070.001 T1027 T1614.001

Log destruction goes well beyond a single command. DeadLock clears the Security, System, Application, and PowerShell channels through the Event Log API, walks the WINEVT Channels registry tree directly, zeroes each channel's Enabled value, and replaces its access permissions with a restrictive descriptor so it can't easily be re-enabled or read. A separate pass through wevtapi.dll clears channels beyond that hardcoded list, including third-party telemetry. The practical takeaway: a channel that's simply missing is evidence in itself, not a sign nothing happened.

Before any of that runs, an embedded, XOR-encoded configuration block gets decoded and checked against the system's default and UI language. Russian, Ukrainian, Belarusian, several other CIS languages, and Iranian, Syrian, Omani, or Yemeni locales all cause the malware to quietly delete itself — a regional-avoidance pattern worth a line in a report, not proof of who's behind the keyboard.

Decentralized recovery infrastructure

This is the detail that earned DeadLock a dedicated write-up. Its victim-facing recovery chat doesn't point at a fixed server — the client resolves the current proxy address from a smart contract on the Polygon blockchain, so seizing one endpoint doesn't sever communications; operators just update the contract. Chat itself runs over Session, a decentralized messenger, rather than a conventional web chat or a single Tor hidden service. The note that starts this whole flow, RECOVERY_CHAT.<UID>.html, is dropped in every drive root and Desktop folder — and is itself a small, complete web application: end-to-end encrypted chat, a paginated leak-site browser, and a file browser, all running client-side with nothing fixed for a takedown to seize.

An affiliate operation, not one crew

Microsoft observed DeadLock deployed by more than one group, including an affiliate linked to both the Lynx and INC ransomware ecosystems. Read alongside the decentralized infrastructure, that points to DeadLock functioning more like a shared tool moving between affiliated operators than one fixed team — which matters both for attribution and for predicting where else these exact TTPs might resurface.

CASE STUDY B

The Gentlemen: A Self-Propagating Go Encryptor

First seen

Mid-2025

Language

Go

Extension

random, e.g. .umc16h

Claimed victims

470+ / 70+ countries

Same primitives, independently chosen

Microsoft tracks the operators as Storm-2697, a ransomware-as-a-service platform that started as a closed operation before recruiting affiliates in September 2025. Its encryption is, again, the Module 1 hybrid pattern: per-file ephemeral Curve25519 keys wrapping XChaCha20 stream-cipher encryption — the identical pair of primitives DeadLock uses, in a Go codebase with no relationship to DeadLock's Rust one. That convergence isn't coincidence so much as a sign of where ransomware tooling has settled: Curve25519 and XChaCha20 are fast, well-regarded, and available as safe, ready-made building blocks in both languages' crypto libraries, sidestepping some of the classic implementation pitfalls of hand-rolled RSA padding. Files under roughly 1 MB are encrypted whole; larger files are split into chunks — DeadLock's 512-byte intermittent blocks solve the same large-file problem with a different specific strategy.

Self-propagation: a worm, not just an encryptor

This is where the two families diverge sharply. DeadLock encrypts what it's pointed at; The Gentlemen, run with a --spread argument, turns into a self-propagating worm — harvesting credentials or reusing the current session token to push copies of itself across the network via hidden SMB shares, PsExec, WMI, scheduled tasks and services, and PowerShell Remoting. Reporting describes upward of twenty distinct lateral-movement methods per target, run in combination rather than one at a time, which is a meaningfully different risk profile from a locker that has to be deployed everywhere by hand. A separate --wipe argument optionally overwrites free disk space after encryption, targeting recoverable fragments a defender might otherwise carve back out.

The same anti-forensics playbook T1490 T1614.001

Underneath the propagation, The Gentlemen runs a checklist that will look familiar: shadow copies and other recoverable artifacts deleted, EDR tooling targeted for termination, and a documented policy of avoiding Russia and other CIS countries. It also exfiltrates data before encrypting — double extortion, same as DeadLock. Initial access has leaned on exploited Fortinet FortiGate appliances and VPN endpoints rather than DeadLock's more opportunistic approach, which matters for a defender: the entry point differs even when almost everything downstream of it doesn't.
