Fundamentals of Encryption

What ransomware actually does to a file, explained from first principles — no math background required.

Encryption turns readable data into unreadable data using a mathematical key. Almost everything ransomware does comes down to two different ways of handling that key.

Here's the smallest possible version of the idea. Shift every letter in a message forward by three places: "HELLO" becomes "KHOOR." The rule — shift by some amount — is the algorithm. The number three is the key. Anyone who knows both can read the message; anyone who only sees "KHOOR" can't, unless they guess the key. Real encryption is the same basic idea — an algorithm plus a key — just with math complex enough that guessing the key isn't remotely feasible. Everything else in this module is really about how ransomware chooses, generates, and protects that key.

Two ways to hand out a key

A shared padlock

One physical key locks and unlocks the same box. Fast and simple — but whoever holds a copy of that key can open every box it's ever locked. If the key leaks, everything it protects is exposed at once. This is symmetric encryption.

A two-key drop box

Anyone can drop a letter through the slot and seal it — that's the public key, safe to hand to a stranger since it only locks. Only the matching private key opens the box. This is asymmetric encryption.

Symmetric vs. asymmetric, in practice

Property Symmetric Asymmetric
Common algorithms AES-256, ChaCha20 RSA-2048, ECC / Curve25519
Speed Very fast — gigabytes per second on modern hardware Orders of magnitude slower; the underlying math doesn't scale to bulk data
Key handling One key does both jobs — it must stay secret everywhere it exists Public half can be distributed freely; only the private half must stay secret
Core weakness A single point of failure — one leaked key, total compromise Computationally expensive; impractical for encrypting large volumes directly

AES is formally defined by NIST in FIPS 197; RSA is one of the algorithms in NIST's FIPS 186-5. These aren't ransomware-specific — they're the same standards banks and governments use.

Why 256 bits?

AES-256 has 2²⁵⁶ possible keys — a number so large that "a lot" undersells it. Even a hypothetical computer checking a trillion trillion keys every second, running since the universe began, would still be nowhere close to trying them all. That's not defense in depth; a correctly generated 256-bit key genuinely isn't findable by guessing. It's exactly why attackers don't try to break the encryption itself — they go after the key, wherever it might still be sitting in memory (Module 5).

The hybrid model: how ransomware actually works

Neither approach alone fits an attacker's needs. Encrypting a whole environment with RSA alone would take far too long — slow enough that defenders could interrupt the attack before it finished. Encrypting with AES alone solves the speed problem, but creates a new one: that AES key has to exist somewhere accessible to the malware, which means a defender who captures memory or reverse-engineers the sample can often recover it.

So ransomware combines both, using each for what it's good at:

  1. 01

    Generate a local AES-256 session key

    Created in memory, unique to this run — never written to disk in plaintext.

  2. 02

    Encrypt the file payload

    Every targeted file is transformed with that key, fast enough to process an entire environment in minutes.

  3. 03

    Wrap the AES key with the attacker's RSA public key

    The public key is embedded in the binary at compile time; the wrapped blob is what actually gets written to disk.

  4. 04

    Destroy the original plaintext key

    Only the unreadable wrapped version survives. Without the matching private key, it cannot be reversed.

The malware itself never carries a decryption key — only a public key, which can lock but never unlock. That's precisely why decryptor tools rarely exist for well-implemented ransomware: without the attacker's private key, a correctly generated AES key is not recoverable by brute force.
